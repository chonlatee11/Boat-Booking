<objective>
Give super_admin a user-management API: create/update staff and pier_admin users bound to one operator and a validated set of piers, list them, and disable/re-enable them — with pier ownership confirmed by a synchronous call to catalog (database-per-service forbids a foreign key).

Purpose: AUTH-04 (super_admin assigns operator + piers), completing AUTH-02 for staff roles, and the admin UI's staff page backend (plan 02-13). Reachable through the gateway admin proxy already allow-listing `boatbooking.identity.v1.UserService`.
Output: `UserService` proto + handler, `app/users.go`, identity → catalog client, integration tests with a fake catalog.
</objective>

## Phase Goal

**As a** customer, staff member or pier_admin, **I want to** sign in with a one-time code and (as an admin) manage operators, piers, routes, boats and prices, **so that** customers can browse the catalog publicly while every admin only ever touches their own operator's piers. *(Restatement of the ROADMAP Phase 2 goal.)*

This plan's slice: **As a** super_admin, **I want to** add a staff member with their operator and piers, **so that** when they sign in they see exactly those piers and nothing else.
