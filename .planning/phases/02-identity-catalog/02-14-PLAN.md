<objective>
Close UAT gap G-02-3: in Mailpit, the Thai body of the OTP email shows as mojibake ("à¸£à¸«à¸±à¸ª...") even though the subject looks fine.

Root cause (from .planning/debug/otp-email-thai-mojibake.md, binding): sendSMTPMessage in services/identity/internal/adapters/notify/notify.go builds the raw message with fmt.Sprintf and adds no MIME-Version, Content-Type or Content-Transfer-Encoding header. Under RFC 2045 an undeclared body defaults to us-ascii, so Mailpit decodes the UTF-8 Thai bytes as Latin-1. The Subject is raw UTF-8 rather than RFC 2047 encoded. It only looks right because Mailpit is lenient with headers. SMTPSender and DevSMSSender both go through this one function. ResendSender sends JSON, so it is not affected and is out of scope.

Fix it once, in the shared function. Use stdlib only (mime, net/mail); no new dependency.

Tracer note: this plan has one task. The fix sits in a single shared function on a path that already works end to end, so a separate tracer slice would add nothing. The task's verify covers the unit-level header check and the real Mailpit round-trip.

Output: notify.go builds a MIME-correct message, and notify_test.go proves it.
</objective>

  <action>
Per D-02 (Mailpit dev delivery) and gap G-02-3, split sendSMTPMessage so the message bytes come from a small pure function: otpMessage(from, to, subject, code string) []byte. sendSMTPMessage keeps its signature and envelope-From parsing and passes otpMessage's result to smtp.SendMail. SMTPSender and DevSMSSender do not change. They already call sendSMTPMessage, so both are fixed by this one change.

otpMessage writes these headers in order, each ending in CRLF: From (verbatim), To (verbatim), Subject (the subject encoded with mime.BEncoding.Encode using charset "UTF-8"; stdlib returns ASCII input unchanged, so the English-only dev SMS subject stays readable), then MIME-Version: 1.0, Content-Type: text/plain; charset=UTF-8, and Content-Transfer-Encoding: 8bit. After those comes a blank CRLF line, then the same body text as today: the Thai and English "your code" line, then the "expires in 5 minutes" line.

Why 8bit and not quoted-printable: this sender only ever talks to Mailpit (dev, D-02). Production email goes through ResendSender's JSON API. So 8bit is the smallest correct choice here.

Keep the code out of every error and log path, as today. Do not log the built message.

Add the unit test TestOtpMessageIsUTF8MIME to notify_test.go, checking the behavior block above with stdlib only (bytes, mime, net/mail, io, strings). Write the test first and confirm it fails against the current message format (there is no Content-Type header today). Then implement.
